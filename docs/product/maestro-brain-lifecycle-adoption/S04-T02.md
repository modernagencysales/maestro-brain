# S04-T02 Lifecycle Adoption Record

**Owner:** S04-T02  
**State:** product instance — durable Slack directory state

## Durable resources

- `providerConnections` remains the Nango-owned Slack connection binding. This
  task consumes the S04-T01 row and requires `teamId`, `apiAppId`, and
  `botUserId` before channel reconciliation can write tenant state.
- `sourceChannels` stores one stable row per Slack channel inside a connection
  generation. `channelKey` is derived from the stable connection key plus Slack
  channel ID, so channel renames update in place and do not create a new key.
- `channelSyncStates` stores per-channel, per-lane cursors for later live,
  recent, deep, and reconciliation workers. Reauthorization keeps existing
  channel keys and cursor rows; stale connection generations are rejected.

## Lifecycle behavior

- Initial reconciliation lists channels only; it never invokes
  `conversations.join` or auto-joins a channel. If initial channel listing fails
  after bot identity verification, the connection remains `error` and no channel
  rows are written.
- Bot membership is copied from Slack `is_member`. Joined channels start at
  `joined_needs_policy`; unjoined channels remain `discovered_not_joined` and
  are not eligible for capture.
- Slack Connect flags (`is_shared`, `is_ext_shared`) are persisted on every
  reconciliation page.
- `expectedGeneration` fences every reconciliation. Replacement, disconnect,
  uninstall, app/team/bot mismatch, or duplicate team/app/bot binding moves the
  old active generation out of `active`, pauses live channel lanes, and stores a
  typed replacement audit before later route/job/outbox adoption tasks consume
  it.

## Compatibility and rollback

The change is additive. Rolling back stops `reconcileChannels` callers and
leaves `sourceChannels` and `channelSyncStates` as inactive diagnostics. No
provider tokens or raw Slack credentials are stored in these rows.
